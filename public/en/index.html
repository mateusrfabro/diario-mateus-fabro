Section III

Standing orders — the rules that stayed

20 of the 125 recorded lessons. Each came from a real case and has an origin, a reason and a way to apply it.

  1. Verify before concludingNever say "done" without running the check and reading its output. Green applies only to the exact tree tested: editing afterwards voids the run.
  2. Mutation testing: prove the test can failA green test is worth something only if it could be red. Revert the fix in a copy and require the suite to fail.
  3. A control with a forced result is not a controlBefore publishing "0 occurrences", ask whether the number could have been anything other than zero.
  4. The conclusion cannot be wider than the testRight query, right number, false sentence. Put the predicate next to the sentence before publishing.
  5. Missing data is not a statementAn empty list caused by missing coverage becomes "there is nothing" and reassures the person who should act. Separate "there is none" from "I don't know".
  6. A queue is not a delivery, and a delivery is not a viewCounting the queue table measures what was enqueued, not what happened. As a denominator, it yields a low, plausible number.
  7. Watch the effect, not only the causeA cause monitor only catches the failure someone already imagined. An effect monitor is a single one and indifferent to the cause.
  8. A backup only exists if it restoresA backup never restored is not a backup; a volume or a replica isn't either. Prove the cycle by destroying real data and bringing it back.
  9. Silent fallback on a critical valueExchange rate, configuration, version and limits never sit behind a try/except with a default. Failing loudly beats publishing a wrong number.
  10. A number outside the code ages on its ownEvery published number comes out of the code in the same run. Patching a paragraph creates two quantities with the same name.
  11. "New to us" is not "just happened"Widening coverage makes history arrive as news. Notify by the date of the event and mark the old ones.
  12. Render the artifact the user receivesA green suite does not prove the screen or the paper. Render the receipt, PDF or email the person actually gets.
  13. Reference data lives with the codeA canonical list in a git-ignored folder only exists on the developer's machine; CI and production degrade silently.
  14. Never analyze on the database that serves the customerA read query can also take production down. The default is a replica or an analytical database, with an identified session and a timeout.
  15. Don't clear a suspect with a non-discriminating signalTo claim "not fraud" or "not a regression", run the detector that would find it. A signal the culprit would also show clears no one.
  16. The PII guard is the leak vectorThe list that proves "no personal data in the delivery" is itself personal data. Derive the target at runtime; don't version it.
  17. Environment identity from configuration, not from data"Is this production?" is answered by reading the deploy configuration, not by the presence of a row that may have been deleted.
  18. Escapes don't survive the shell\b and \n written through a heredoc reach the file as control characters. The terminal hides it; the regex never matches.
  19. A subagent judges against a snapshotAn agent without live access gets the reasoning right and the fact wrong. In infrastructure that changes weekly, the snapshot ages in days.
  20. Don't rely on AI aloneGuess before asking for the number. AI speeds things up; the judgment is still mine.

Masthead — how I work

Paired with AI agents, and with a system that keeps the same mistake from happening twice.

Layered memory

Every project has a memory index of its live pitfalls. What applies to another project moves up to a global memory: a lesson with an origin, a reason and a way to apply it.

A gate closes the promotion

Promoting a lesson means writing it to disk, to the human index and to the machine index. That step failed twice without a symptom; today a script checks all three and has a mode that proves it can go red.

Mutation as a habit

66 of my 716 commits on Avisa Edital record mutation testing: the defect is reintroduced and the test must fail before the fix counts.

Agents with a role, not autonomy

15 specialized agents (quality, security, testing, UX, content review, growth) work in parallel. What the reviewers find is reproduced before it becomes a change.

Where we left off

Every project has a resume file the next session reads first: state, the business owner's decisions and open items, with dates.

## Standing orders (lessons)

20 of the 125 recorded lessons, published here.

1. **Verify before concluding** — Never say "done" without running the check and reading its output. Green applies only to the exact tree tested: editing afterwards voids the run.
2. **Mutation testing: prove the test can fail** — A green test is worth something only if it could be red. Revert the fix in a copy and require the suite to fail.
3. **A control with a forced result is not a control** — Before publishing "0 occurrences", ask whether the number could have been anything other than zero.
4. **The conclusion cannot be wider than the test** — Right query, right number, false sentence. Put the predicate next to the sentence before publishing.
5. **Missing data is not a statement** — An empty list caused by missing coverage becomes "there is nothing" and reassures the person who should act. Separate "there is none" from "I don't know".
6. **A queue is not a delivery, and a delivery is not a view** — Counting the queue table measures what was enqueued, not what happened. As a denominator, it yields a low, plausible number.
7. **Watch the effect, not only the cause** — A cause monitor only catches the failure someone already imagined. An effect monitor is a single one and indifferent to the cause.
8. **A backup only exists if it restores** — A backup never restored is not a backup; a volume or a replica isn't either. Prove the cycle by destroying real data and bringing it back.
9. **Silent fallback on a critical value** — Exchange rate, configuration, version and limits never sit behind a try/except with a default. Failing loudly beats publishing a wrong number.
10. **A number outside the code ages on its own** — Every published number comes out of the code in the same run. Patching a paragraph creates two quantities with the same name.
11. **"New to us" is not "just happened"** — Widening coverage makes history arrive as news. Notify by the date of the event and mark the old ones.
12. **Render the artifact the user receives** — A green suite does not prove the screen or the paper. Render the receipt, PDF or email the person actually gets.
13. **Reference data lives with the code** — A canonical list in a git-ignored folder only exists on the developer's machine; CI and production degrade silently.
14. **Never analyze on the database that serves the customer** — A read query can also take production down. The default is a replica or an analytical database, with an identified session and a timeout.
15. **Don't clear a suspect with a non-discriminating signal** — To claim "not fraud" or "not a regression", run the detector that would find it. A signal the culprit would also show clears no one.
16. **The PII guard is the leak vector** — The list that proves "no personal data in the delivery" is itself personal data. Derive the target at runtime; don't version it.
17. **Environment identity from configuration, not from data** — "Is this production?" is answered by reading the deploy configuration, not by the presence of a row that may have been deleted.
18. **Escapes don't survive the shell** — \b and \n written through a heredoc reach the file as control characters. The terminal hides it; the regex never matches.
19. **A subagent judges against a snapshot** — An agent without live access gets the reasoning right and the fact wrong. In infrastructure that changes weekly, the snapshot ages in days.
20. **Don't rely on AI alone** — Guess before asking for the number. AI speeds things up; the judgment is still mine.
